# OpenSBI 引导与 S-mode Payload 运行调试记录 (2026-05-22)

## 1. DCache 模块中 `LSU_LR` 的遗漏修复 (RTL 修正)
在调试 OpenSBI 启动过程中，发现其引导流程由于自旋锁和同步失败卡死在 HSM 无效状态错误中。经过追踪，发现核心原因为 `dcache.sv` 中的 Bug。

### Bug 原因与修复方案
- **原因**：在数据缓存的 `extract_load` 选择逻辑中，未匹配 `LSU_LR` 操作码。导致 `lr.w` 指令在 DCache 中命中读取时，传回给流水线的值被清空为 `0`，进而使 OpenSBI 无法正确获得同步锁状态。
- **修复**：修改了 [dcache.sv](file:///e:/vivado_project/OOOcpu_design/Triathlon/npc/vsrc/cache/dcache.sv)，在提取 Load 数据的选择条件中将 `LSU_LR` 与普通 Load 操作一并包含。
- **结果**：修复后，OpenSBI 能够正常通过 `lr.w` 和 `sc.w` 的同步代码段，顺利完成多核/单核初始化，并跳转至 S-mode 目标 Payload 运行。

## 2. S-mode Console 打印调试 (SBI DBCN 扩展)
在使用 S-mode 汇编测试负载 ([payload.S](file:///e:/vivado_project/OOOcpu_design/Triathlon/echo_payload/payload.S)) 时，最初控制台未产生可见输出。

### 原因定位
- OpenSBI 废弃或忽略了旧版 Legacy SBI Putchar 调用（EID 1）。
- 在现代 OpenSBI (v1.8) 规范下，S-mode 的调试输出应改用 **SBI DBCN (Debug Console) 扩展**。

### 实现方案
重构了 `payload.S` 的控制台输出逻辑，使用 DBCN 扩展标准：
- **EID (Extension ID)**: `0x4442434E` ('DBCN')
- **FID (Function ID)**: `2` (write_byte)
- **a0**: 要写入的字符字节值

更新后的汇编片段：
```assembly
    # DBCN write_byte: EID = 0x4442434E, FID = 2, a0 = byte
    li a7, 0x4442434E
    li a6, 2
    mv a0, a1
    ecall
```
经测试，控制台成功输出了 `"SBI DBCN Output Works!\r\n"`，证明 S-mode 引导及运行路径已彻底打通。

## 3. 工作流沉淀与文档更新
为了便于后续的调试与复现，我们将这套 **编译 - 合并 - 调试** 的工作流沉淀到了 [CLAUDE.md](file:///e:/vivado_project/OOOcpu_design/Triathlon/CLAUDE.md) 中：

### 3.1 完整执行流程
使用单条命令即可完成一站式编译与仿真，并输出详细指令轨迹（Commit Trace）：
```bash
wsl bash -c "cd echo_payload && make && cd .. && python3 merge.py && make -C npc sim IMG=/mnt/e/vivado_project/OOOcpu_design/Triathlon/fw_combined.bin DIFFTEST_SO= ARGS='--commit-trace --max-cycles=10000000' > npc/sim_trace.log 2>&1"
```

### 3.2 关键参数设计
- **`DIFFTEST_SO=`**: 置空。由于 S-mode 特权级指令、MMU 虚实地址转换及 OpenSBI 硬件初始化涉及复杂外设（如 PLIC），无法与纯用户态/裸金属的参考模型 NEMU 对齐。
- **`ARGS='--commit-trace --max-cycles=10000000'`**:
  - `--commit-trace`: 输出指令提交日志，利于跟踪控制流和寄存器改变。
  - `--max-cycles=10000000`: 限制仿真最大周期，避免无限循环时磁盘空间被 Trace 日志写满。
