# 实验日志 - 2026年5月22日

## 1. 遇到的问题与分析过程

在移植 Linux 到 Triathlon (RV32IMAC) 乱序处理器的过程中，遇到了仿真极早期的严重 Boot failure。表现为 CPU 陷入了对 `0x00000000` 地址的无限 `[TRAP]` 循环（`cause=12`，指令页错误）。

### 1.1 架构设计 Bug：推测性页错误异步注入
最初排查时，怀疑是 IFU 取指队列 Flush 时对 PC 的更新不当，引发了取指错乱。然而在仔细追踪微架构信号链条（IFU -> BPU -> MMU -> Backend）后，发现了更深层的**根本性硬件架构设计缺陷**：

*   **缺陷行为：** 当 BPU 由于陈旧数据（或异常跳转后的执行历史）错误预测下一条 PC 为 `0x00000000` 时，IFU 推测性地向 MMU 发起该地址的请求。MMU 理所当然地抛出 `Instruction Page Fault` 异常。IFU 随后向 Backend 发出 `ifetch_fault` 警报。
*   **致命漏洞：** Backend 中的 CSR 模块在接收到 `ifetch_fault_valid_i` 时，**立刻且异步地（Asynchronously）**注入了该异常并强制 Flush 整个流水线。在乱序处理器中，针对推测路径的异常**必须**随指令在 ROB 中排队，并在该指令成为最老指令（Commit）时才能触发。CSR 的这种全局异步处理直接绕过了 ROB，把原本在正确执行路径上的指令（如异常处理入口 `0xc0486c98`）连同流水线一起销毁，导致 CPU 再次重新陷入异常，形成死循环。

### 1.2 修复策略验证
为了在不重构整个 ROB 取指错误传递路径的前提下低成本修复此问题：
*   撤销了前期在 `ifu.sv` 引入的强行写入 `redirect_pc_i` 导致的双重取指 (Double-fetch) 错误（该错误曾导致流水线死锁）。
*   在 `backend.sv` (Line 1842) 的 `csr_ifetch_fault_inject` 注入条件中，**增加了 `&& rob_empty` 的门控**。
*   **修复原理：** 这个优雅的补丁确保了只有当流水线中更老的、正确的指令全部执行并提交完毕（此时 ROB 清空）时，指令页错误才会被当作真实的异常注入。如果该错误只是推测性的，早于它的正确分支指令会在 ROB 排空前就完成 Flush 操作，从而将推测性错误自动丢弃。

## 2. 当前最新状态与新线索 (sim_trace_fix3.log)

应用 `rob_empty` 硬件门控并重新运行仿真 (`sim_trace_fix3.log`) 后，推测性死循环的硬件问题已被成功拦截。然而，日志显示我们**依然陷入了对 `0x00000000` 的 TRAP 循环**。

经过深入分析，这代表了一个截然不同的问题性质：**现在的 0x00000000 报错不再是推测执行的受害者，而是软件层面（内核或 OpenSBI）真正地向 0x00000000 发起了非法的跳转！**

日志线索如下：
1. 仿真极早期出现了 `[TRAP] pc=80004dd8 cause=2`（非法指令，在 M-mode OpenSBI 范围内）。
2. 随后异常等级下降到了 S-mode (`to_s=1`)，并开始在虚拟地址 `c0486c98`（Linux 内核异常向量表入口）处理异常。
3. 最终 CPU 卡在了 `[TRAP] pc=00000000 cause=12 tval=00000000 stvec=c0486c98`。

**分析结论：**
由于 ROB `rob_empty` 的保护伞生效，只有当跳往 0 地址的指令**真正处于正确执行路径的最前端**时才会触发 Trap。这意味着 Linux 内核的异常处理程序（`handle_exception`）在处理前期发生的错误时，其内部的 `sret`（返回了非法的 `sepc=0`）或者 `jalr` 指令实际上指向了 Null 地址。系统由于栈损坏、未初始化状态或前期 Illegal Instruction 处理不当引发了内核崩溃级 Panic。

## 3. 下一步行动方向

硬件架构级的推测页错误漏洞已完成封堵，接下来的工作重心全面转向**软件异常执行流调试**。

1. **提取指令流迹 (Instruction Trace)：** 开启 NPC 的 `--dump-wave` 选项（或在 `backend.sv` 打开 `be_trace_en_q` 相关的指令追踪），精确抓取 CPU 从跳转到 `0xc0486c98` 开始，一直到最终引发对 `0x00000000` 跳转的具体那一条指令（追查是 `sret` 还是寄存器损坏的 `jalr`）。
2. **排查最初始的 Illegal Instruction：** 定位 `80004dd8` 这条指令的内容。它是 OpenSBI 初始化中的哪一步？是否因为某些 CSR 未实现或配置缺失导致了多米诺骨牌效应，最终摧毁了 Linux 的启动栈。
3. **结合 Linux vmlinux 反汇编：** 获取匹配的 vmlinux ELF 文件进行 `objdump`，将波形和 Trace 日志与汇编代码对照，定位内核崩溃的确切代码行。
